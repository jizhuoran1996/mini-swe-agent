# 构建场景：默认完整构建，增量作为可选对照

本包的基本单位是一个工程交付目标：从指定源码构建可使用的产物，完成指定测试，并使独立使用方能够消费该产物。60 个 ID 对应 60 个主工程。编译选项、并行度、缓存状态和补丁是同一个任务的实验配置。

## 1. 默认场景：完整源码构建与测试

默认初始环境包含源码、子模块、固定工具链与已下载的依赖，目标工程的构建目录、安装目录及对象缓存为空。任务执行包含该工程所需的 configure/generate、compile、link、package/install 和正式测试；实际阶段由项目构建系统决定。例如，有些工程通过一次构建命令完成编译和链接，不能仅凭命令边界伪造独立链接计时。

源码检出、依赖下载和基础镜像制作在这一场景中预先完成。环境恢复成本仍按 THENAME 的生命周期口径记录，但与工具执行阶段的编译成本分开。一个官方命令可以完成真实且充分的工程工作，不要求 agent 刻意拆成多次调用。

“完整”指完整完成所声明的构建目标，例如 CPU PyTorch wheel、宿主架构 Clang 工具链或包含特定模块的 FFmpeg；不等于启用仓库中的所有平台、GPU 后端、插件和云端 CI。

## 2. 可比较的构建场景

| 场景 | 起始状态 | 实际工作 | 适合观察 |
|---|---|---|---|
| clean-source-build（默认） | 依赖已备齐，目标工程无构建结果 | 真实配置、编译、链接、打包、测试 | CPU 工作、链接峰值、文件/进程活动和工作空间增长 |
| clean-build-with-object-cache | 独立空构建树，声明过的对象缓存可用 | 正常构建流程与实际命中情况 | 缓存访问、元数据成本、状态恢复及缓存策略 |
| incremental-change | 已验证的基线构建树，冻结的功能或配置变化 | 受影响目标重建、回归测试、产物更新 | 依赖失效传播和跨轮构建状态复用 |
| no-op-rebuild（诊断） | 无源码或配置变化的已有构建树 | 构建图检查和必要的工具启动 | 图遍历、文件检查和最低调度开销 |
| acquisition-plus-build（可选） | 固定本地/远端依赖服务和空下载缓存 | 声明的获取流程加构建测试 | 依赖传输与构建之间的相互影响 |

上述场景分别报告，不合并成新的工程数量。缓存命中不等于完成了相同数量的编译工作，应同时记录命中、未命中和实际执行的编译动作。Ninja 的工作是根据依赖图调度需要执行的构建动作；ccache 则可能直接复用既有编译结果。参见 [Ninja manual](https://ninja-build.org/manual.html) 和 [ccache manual](https://ccache.dev/manual/latest.html)。

## 3. 增量变化如何构造

优先使用任务卡中已指定的合法特性开关或模块变化。若使用源码补丁，builder 必须先选择具体基线 revision，将补丁内容、适用路径和预期功能变化冻结，并提供变化前后均有意义的验收。没有绑定到源码的补丁建议保留在 builder 工作项，不伪装成已存在的 upstream bug 或 PR。

增量测试保留依赖闭包需要的构建状态。不得以一个 `touch`、重复构建或提高 `-j` 代替新的功能交付。no-op 和 touch-only 可以是单独标记的诊断操作，不计为独立 agent task。

## 4. 五种缓存必须分开声明

1. **依赖下载缓存**：源码包、Maven/Gradle/npm/Cargo/Go 依赖、Python 构建依赖和 Bazel 外部仓库。
2. **目标工程构建树**：对象文件、生成源码、依赖文件、构建数据库、配置探测结果。
3. **编译或 action cache**：ccache、sccache、Bazel local/remote action cache 等。
4. **操作系统页缓存**：源码和产物的文件缓存，受宿主、guest 与实际访问影响。
5. **sandbox 镜像与快照**：包含哪些源码、依赖、构建产物和运行状态。

下载缓存可以预热，同时保持目标工程编译结果为空。不要把“空构建树”称作“所有缓存冷启动”。全局页缓存控制由受测平台的宿主协议决定，普通 sandbox 任务不执行宿主级 cache flush。Bazel 的依赖仓库缓存与 action 输出缓存也不是同一个对象，参见 [Bazel remote caching](https://bazel.build/remote/caching)。

## 5. 配置控制与资源限制

固定构建 jobs、测试 jobs、链接器线程、LTO 模式及运行时线程设置；CPU 配额和内存限制属于 sandbox 配置，不能用更少编译目标补偿较慢后端。默认按相同源码、目标、测试集合和并行配置比较后端。若研究配额自适应或缓存策略，将其作为显式实验变量，并保留实际采取的动作。

同一个任务的 core/reference/extended 配置改变有真实用途的目标范围或测试范围。小工程可主要增加有意义的特性或测试，不能通过重复运行把它包装成大工程。大型工程则从有界宿主目标起步，逐步扩展组件、工具链阶段或可选设备后端。
