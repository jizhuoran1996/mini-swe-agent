# 后端与GPU能力

GPU扩展以能力合同选择任务。原CPU后端能启动Bash，并不说明它已经具有本任务所需的GPU路径。

## 首版建议的比较范围

- 先建立 Native+GPU 与容器+GPU 的功能参考：确认应用真实使用被分配设备，CPU/预处理/数据加载也在声明的计量范围内。
- gVisor可以列为GPU候选后端。其官方文档描述nvproxy代理应用与宿主NVIDIA驱动的交互，并限定支持的GPU/驱动/API组合；实现时固定匹配版本并逐任务验证。不要把文档中的示例通过当作本包任务通过。
- VM后端需要独立验证设备直通、虚拟GPU或其他实际设备访问方式。写明guest/host驱动、设备拓扑、IOMMU/互联与计量位置；不从VMM名称推断支持情况。
- CPU-only后端保留为不满足GPU能力的记录；不能静默CPU fallback后参与GPU性能排名。

## 逐任务能力字段

所需GPU API/计算精度、框架算子/扩展、设备内存档位、多卡collective/P2P、统一内存或out-of-core、图形/视频编解码（仅需要时）、host共享内存/文件系统、后台进程与长驻服务，以及模型/数据格式。

后端能力探测用真实小输入验证CUDA计算、数据往返和输出，再用正式输入进行准入。状态记为supported、unsupported、failed或unmeasured，保留原因。通用runtime成功创建不能代替应用能力检查。

本包以NVIDIA/CUDA生态来源为主。其他GPU平台可以建立明确的移植配置并通过同一语义验证；未验证的移植不直接标成支持。

## 控制层负责的内容

分配设备、注入本轮GPU标识与环境、创建/销毁sandbox、准入与排队、运行期间的策略事件、监测及异常回收。任务提供真实应用操作；不在Bash任务中偷偷访问宿主容器socket或把重计算交给未计量服务。
