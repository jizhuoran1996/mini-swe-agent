# Cloud GPU sandbox 场景

这些配置复用 60 个任务，不新增 task IDs，也不规定新的调度算法。先固定任务、规模和实际轨迹，再改变一个需要研究的系统因素。

| 场景 | 工作负载选择 | 控制变量 | 主要结果 |
|---|---|---|---|
| S0 独占参考 | 每个 pilot 顺序运行 | 相同模型/数据/精度、明确冷/热状态 | 功能、GPU 活动、显存/host 成本、实际资源画像 |
| S1 加载与首次执行 | 不同模型服务、视觉/视频模型 | 相同模型复用 vs 多模型；冷/热文件/JIT缓存 | ready、首个有效结果、加载流量、加载时显存与host峰值 |
| S2 驻留与再访问 | 保留模型、图或向量索引的轨迹 | 记录等待、保持驻留 vs 声明的应用重载/offload策略 | 等待期GiB·s、后台活动、恢复后有效结果延迟 |
| S3 长短混部 | 持续训练或大批处理 + 有限交互请求 | 固定到达与同一设备预算；声明的独占/共享配置 | 每类goodput/slowdown、排队、OOM、显存占用 |
| S4 突发与同时唤醒 | 多个已初始化session | 平滑到达 vs 同时进入真实请求阶段 | 尾延迟、准入等待、峰值、最大可持续提交压力 |
| S5 多卡协作 | 有多卡参考实现的任务 | 固定GPU数/拓扑后比较后端；另组扫描GPU数 | collective开销、卡间偏斜、完成时间、资源成本 |
| S6 取消与资源回收 | 训练、生成或驻留服务 | 在语义阶段取消；后续正常session复用worker | 取消至停止/释放、残留进程、后续任务时延 |
| S7 应用保存与恢复 | 模型checkpoint、索引、仿真状态 | 固定保存点与后续请求 | checkpoint成本、恢复成本、状态正确性 |

MIG、MPS、CUDA可见设备、GPU time slicing、CPU offload和模型卸载是不同配置，按真实能力分别描述。GPU共享并不自动带来隔离保证或可透明抢占。任务不负责实现这些机制，controller/backend adapter负责执行已选择的配置。

任务默认只使用提供的受控输入与数据服务。业务输入的网络获取可以成为一个单独场景；不在默认GPU执行对照中把公网模型下载延迟混入GPU完成时间。

有限服务请求以真实记录集为基础，重复请求作为重复/缓存场景显式标注，不将反复发送同一prompt当作独立输入。负载生成器和controller的资源同时计量，避免把它们的瓶颈归因GPU后端。

比较共享GPU时，先用相同硬件、驱动、软件、精度和总资源预算建立对照；关闭/开启某策略都要记录实际设备分配。结果中报告失败与未完成，不能从成功样本的低延迟推断整个策略更好。
