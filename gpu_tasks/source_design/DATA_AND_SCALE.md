# 正式输入与规模设计

## 1. 本包怎样回应“大 GPU workload”

60 个任务按应用目标组织，每题同时给出 debug、reference_large、optional_scale_out。正式规模来自真实模型、数据集、图、序列、影像体积、视频分辨率或物理系统。debug 只为实现调试；规模、batch、精度、种子、并行度都不增加 task 数量。

大型工作负载可以表现为较大的显存状态、持续的有效计算、较大的数据/模型传输，或多 GPU 协作。不能要求每题同时填满所有维度。任务变轻时据实归类；不填零数组、不复制向量、不循环短视频、不添加无用 epoch 或重复输出凑负载。

## 2. 硬件档位是实现目标

| 档位 | 计划配置 | 适用方式 |
|---|---|---|
| T1 | 单卡约 24–48 GiB 显存 | 首批工程适配、较长数据作业、常规视觉训练、部分模型服务 |
| T2 | 单卡约 80 GiB 显存 | 更大模型、长上下文、高分辨率视频、较大的常驻状态 |
| T3 | 单机 2–8 卡，逐题声明每卡容量与互联 | 模型/状态超出单卡或源工作负载需要多卡；包括可选分布式图/训练 |

这些是设计档位，不是已测最低需求或能保证运行的配置。task card 的具体模型精度、全局 batch、输入尺寸、优化器和并行策略共同决定用量；必须完成容量校准。不要把 70B 参数、压缩下载大小或数据文件大小直接转成实际显存。

部分科学训练、超大图和全量预训练会很长。它们放入 advanced 或可选规模；默认 pilot 选择可建立有效参考流程的代表。完整源 benchmark 的训练收敛协议与 THENAME 明确派生的有限训练/继续训练协议分别标记。减少数据、改变训练起点或目标后，不声称是原官方 benchmark 成绩。

## 3. 每个正式实例需要冻结的内容

asset manifest 记录：来源 URL/仓库、不可变 revision、模型/tokenizer/processor/config 的独立版本、数据集版本与 split、选取规则和样本 IDs、每个对象哈希/字节数、格式/精度、许可与访问方式、初始文件路径、输出/临时目录及 cache 策略。

某来源要求注册、研究许可或下载授权时，交付获取配方和状态；本包不包含第三方权重、训练数据或授权凭据。公开 URL 也不自动代表可以重新分发所有内容。

对于大型源数据，可以使用公开的合法 split、正式子集或冻结的唯一记录清单。任务卡给出来源规模与选择方式，实施后记录实际条数和字节数。子集会改变 ANN ground truth、图结构或统计分布时，重新生成匹配 oracle，不能套用全量答案。

## 4. 数据准备与任务执行

镜像构建、依赖下载、模型/数据获取列为准备。任务要求完成的训练、模型适配、推理、索引、仿真和产物写出发生在 task 期。数据预处理若属于交付目标则计入任务；若作为冻结初态，则保存生成过程和哈希。不可把主要 GPU 工作放进 grader。

同一输入可有 GPU-resident 与流式/分块执行配置。原软件允许的 out-of-core 或 offload 是合法配置，但必须冻结并单独画像，不能在不同后端中悄悄改变。

## 5. 先做代表，再扩规模

先在 debug 验证源码与 oracle，再在 reference_large 跑实际产物。若参考运行已足够重，继续增大只增加时间而不提供新行为时，不必扩大。若来源流程实际很轻，可以保留为交互任务或换正式输入；不能仅靠超长时间预算宣称 GPU-heavy。

每题具体的 source workload、数据和规模配方见 `task_briefs/`。完整目录见 `TASK_CATALOG.md`。
