# 任务实例、阶段与验收

## Task、instance、trajectory 的关系

本包给出60个有具体来源和交付目标的canonical task设计。一次task可以用不同的正式输入清单构造多个instance；同一instance在不同agent/model配置下可以采集不同trajectory。三个数量分别报告。改变batch、精度、GPU数、seed、runtime或是否resume不会增加canonical task数量。

卡片的reference_large描述完整生产规模。长任务可以保留为小时级或更长的轨迹，也可以建立有明确生产目标的有限实例：例如一组完整视频、一批完整三维病例、一份真实文档分片，或从声明checkpoint开始的一段训练交付。实例必须在采集前重新冻结目标、初态、输入ID、工作量和oracle。不能在执行中截断源任务、丢弃未完成部分，再报告成原完整任务成功。

## 初始任务与后续请求

需要处理新输入的continuation使用一份预先冻结的完整请求集合，分成互不相交的initial与continuation子集；正式全量是二者的并集。将同一请求再次提交给常驻服务属于repeat/revisit，单独记录，不增加unique input数量。产物重新导出、查询已生成结果、已有checkpoint续跑分别是不同类型的状态复用。

后续阶段按实际依赖推进，不能把整份后续请求提前交给agent后又声称测到了再次访问。记录到的模型等待保留在阶段之间。每个阶段是否保持进程、模型权重、KV、图索引或科学状态，由实际运行和场景声明共同确定；仅有输出文件复用不证明GPU状态驻留。

## Agent看到什么

`task_briefs/`是实施者规格，包含oracle和负例，不能整个挂入agent可见环境。`agent_prompts/`给出任务目标、要求与后续请求的模板；builder还需注入实例路径、已冻结配置及设备预算。初始提示和后续提示分别交付。训练所需标签属于输入；保留集答案、被修复图像的干净原图、重建任务的完整原网格及独立参考结果只给验证器。

## 三个独立判断

1. **执行完整性**：声明的真实输入已处理，产物/状态可以重新打开，ID与版本一致，无遗漏、重复填充或虚假完成。服务任务还需要本轮端点的后续请求验收。
2. **任务质量**：分类准确率、生成质量、检索质量、SQL正确性或科学误差按固定参考协议校准。模型并不需要对每个样本都答对；预期模型错误与超时、OOM、进程丢失、损坏产物分别记录。
3. **资源准入**：主要GPU工作确实发生，资源形态达到该画像的声明。功能通过不代表GPU-heavy；资源高也不代表任务正确。

数值或学习任务通常采用固定模型/输入/算子配置下校准的aggregate质量门槛，并保留逐项结果。不能要求另一后端生成完全相同的checkpoint字节或媒体字节；也不能只接受一份自报score。正式replay固定记录的命令、训练更新预算、采样方案和终止规则；若源流程按early stopping或固定墙钟选预算，应在参考采集后冻结实际工作，而不是让每个后端自行改变工作量。

Oracle可以重载模型、抽样执行、重算结果或校验守恒关系，其开销单独记账。主要训练、索引、生成和模拟仍在真实任务工具执行中完成。
